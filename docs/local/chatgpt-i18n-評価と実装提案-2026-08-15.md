# 1\. まず、このプロジェクトが何を解決しているのか

i18n+は単なる「翻訳ライブラリ」ではありません。

大きく分けると、

1.  **プラグイン内部のi18n機構**
    
2.  **外部翻訳辞書**
    
3.  **翻訳辞書を管理する別のObsidianプラグイン**
    
4.  **翻訳を後から上書きするOverlay**
    
5.  **辞書の共有・クラウド配布**
    
6.  **既存プラグインをi18n化するcodemod**
    

を一つの仕組みにまとめています。

特に重要なのが、

> **i18n+がインストールされていなくてもプラグインは動く**

という設計です。

プラグイン側には約150行程度のself-contained adapterをコピーし、i18n+が存在すれば連携、存在しなければ単独動作します。[![](https://www.google.com/s2/favicons?domain=https://github.com&sz=128)GitHub+1](https://github.com/open-obsidian-i18n/i18n-plus)

これは設計としてかなり良いです。

* * *

# 2\. 中核の設計はかなり適切

実際の `adapter.ts` を見ると、かなりシンプルです。

概念的には、

```
plugin  │  ├─ built-in translations  │  ├─ external translations  │  └─ t(key)        │        ├─ external dictionary        ├─ current built-in locale        ├─ previous successful locale        ├─ base locale        └─ raw key
```

という構造です。[![](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com&sz=128)GitHub](https://raw.githubusercontent.com/open-obsidian-i18n/i18n-plus/main/templates/adapter.ts)

これはi18nとしてかなり合理的です。

特に、

```
External dictionary        ↓Built-in current locale        ↓Last successful locale        ↓Base locale        ↓Raw key
```

というfallback chainは面白いところです。

通常なら、

```
ja → en → key
```

くらいで済ませます。

i18n+はさらに、

```
ja → 前回正常だったlocale → en → key
```

という考え方を入れています。[![](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com&sz=128)GitHub](https://raw.githubusercontent.com/open-obsidian-i18n/i18n-plus/main/templates/adapter.ts)

ただし、**ここは私はそのまま採用しません。**

後述します。

* * *

# 3\. 一番評価できるのは「外部辞書」と「組み込み辞書」の分離

ここがこのプロジェクトの一番良いところです。

例えば自分のプラグインを、

```
locales/  en.ts  ja.ts
```

としておく。

そしてi18n+側から、

```
plugin-id.ja.jsonplugin-id.zh.jsonplugin-id.de.json
```

を追加できる。

すると、

```
あなたのプラグイン    │    ├── en    └── ja          ↑          │       自前翻訳              ＋
      i18n+          │          ├── zh          ├── de          ├── fr          └── ...
```

という構造になります。

つまり、

**「作者が責任を持つ翻訳」と「コミュニティが追加する翻訳」を分離できる。**

これは非常に良い設計です。

しかも外部辞書を使う場合でもnpm依存にはなりません。[![](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com&sz=128)GitHub+1](https://raw.githubusercontent.com/open-obsidian-i18n/i18n-plus/main/templates/adapter.ts)

# 4\. Obsidianとの相性も良い

Obsidianのプラグインは基本的にTypeScript/JavaScriptで、公式のsample pluginもTypeScript + esbuildという構成です。[![](https://www.google.com/s2/favicons?domain=https://github.com&sz=128)GitHub+1](https://github.com/obsidianmd/obsidian-sample-plugin)

したがって、

```typescript
this.t("Some text")
```

という薄い抽象化は非常に自然です。

例えば、

```typescript
new Notice(this.t("Export completed"));
```

や、

```typescript
setting  .setName(this.t("Language"))  .setDesc(this.t("Select the interface language"));
```

という構造にできます。

これは通常のi18n設計として正攻法です。

# 5\. 一方、「翻訳キー」に原文文字列を使っているのは私は微妙だと思う

ここは重要です。

i18n+の例は、

```typescript
this.t("Hello, {name}!")
```

です。[![](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com&sz=128)GitHub](https://raw.githubusercontent.com/open-obsidian-i18n/i18n-plus/main/templates/adapter.ts)

つまり、

```
key = 英語原文
```

です。

辞書は、

```json
{  "Hello, {name}!": "こんにちは、{name}さん！"}
```

になります。

これは小規模プラグインでは非常に楽です。

しかし本格的には、

```typescript
t("greeting.hello", { name })
```

として、

```typescript
{    "greeting.hello": "Hello, {name}!"}
```

の方が良い。

### 原文key方式

**メリット**

-   翻訳開始が非常に簡単
    
-   keyを考えなくていい
    
-   codemodとの相性が良い
    
-   英語原文そのものがfallbackになる
    

**デメリット**

-   英文を変更するとkeyも変わる
    
-   翻訳が全部無効になる
    
-   同じ文でも意味が違うと困る
    
-   文言修正が翻訳辞書の変更扱いになる
    

例えば、

```typescript
t("Open")
```

が、

```
開く
```

なのか、

```
開いている
```

なのかは文脈依存です。

また、

```typescript
t("Export")
```

を

```
Export
```

から

```
Export data
```

に変更すると、翻訳辞書上は別keyになります。

# 6\. ただし、個人開発なら原文key方式は「悪くない」

ここは重要なバランスです。

一般論では、

> semantic keyを使え

となります。

しかしあなたのような**個人開発の小～中規模Obsidianプラグイン**なら、

```typescript
t("Export")t("Import")t("Settings")t("Language")
```

程度でも十分です。

むしろ、

```typescript
t("settings.language.label")t("settings.language.description")t("commands.export")t("commands.import")
```

と大量のkeyを管理する方が面倒になる可能性があります。

したがって私は、

### 小規模

```typescript
t("Export")
```

### 大規模化したら

```typescript
t("settings.export")
```

へ移行

くらいが現実的だと思います。

# 7\. i18n+の「codemod」はかなり便利だが、過大評価しない方がいい

ここも実際に調べる価値があります。

i18n+には、

```
i18n-codemod.cjsextract-keys.cjsinject-i18n.cjsgenerate-report.cjs
```

があります。[![](https://www.google.com/s2/favicons?domain=https://github.com&sz=128)GitHub](https://github.com/open-obsidian-i18n/i18n-plus)

既存コードから、

```typescript
.setName("Language")
```

などを、

```typescript
.setName(this.t("Language"))
```

へ変換していく仕組みです。

さらにASTを使ってmigration workflowをGitHub Actionsから実行する構成まで用意されています。[![](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com&sz=128)GitHub](https://raw.githubusercontent.com/open-obsidian-i18n/i18n-plus/main/docs/I18N_MIGRATION_GUIDE.zh-CN.md)

これは、

**既存の巨大プラグインをi18n化する**

場合にはかなり価値があります。

しかし、新規プロジェクトなら、

> これを使うためにi18n+を導入する

必要はありません。

* * *

# 8\. むしろcodemodには注意点がある

Migration Guide自身が、

-   動的文字列
    
-   配列内文字列
    
-   複雑なDOM
    
-   string concatenation
    
-   動的な値
    

などは手作業が必要だと説明しています。[![](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com&sz=128)GitHub](https://raw.githubusercontent.com/open-obsidian-i18n/i18n-plus/main/docs/I18N_MIGRATION_GUIDE.zh-CN.md)

例えば、

```typescript
.setDesc("Time: " + DateTime.now())
```

は、

```typescript
.setDesc(  this.t("Time: {time}", {    time: DateTime.now()  }))
```

へ手直しする必要があります。

つまり、

> **codemodでi18n化できる**

というより、

> **codemodで機械的な部分をかなり削減できる**

と考えるべきです。

# 10\. 特に「Obsidian APIの標準機能」ではない

ここも重要です。

i18n+はObsidian公式のi18n APIではありません。

公式のObsidian plugin APIには、当然ながらPlugin、App、WorkspaceなどのAPIがありますが、i18n+のような第三者プラグイン向け翻訳APIが標準化されているわけではありません。[![](https://www.google.com/s2/favicons?domain=https://github.com&sz=128)GitHub+1](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts)

したがって、

```typescript
window.i18nPlus
```

という独自global APIに乗ることになります。[![](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com&sz=128)GitHub+1](https://raw.githubusercontent.com/open-obsidian-i18n/i18n-plus/main/templates/adapter.ts)

ここには当然、

```
i18n+が開発停止        ↓あなたのプラグインはどうなる？
```

という問題があります。

幸い設計上は、

```
i18n+なし   ↓built-in localeだけで動作
```

なので、**このリスクをかなりうまく緩和しています。**

これは高く評価できます。

# 11\. さらに気になるのが「i18n+による外部辞書上書き」

仕組みとして、

```
External Dictionary       ↓Built-in Dictionary
```

です。[![](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com&sz=128)GitHub](https://raw.githubusercontent.com/open-obsidian-i18n/i18n-plus/main/templates/adapter.ts)

つまり作者が、

```typescript
t("Export")
```

に対して、

```
日本語: 書き出す
```

と決めても、外部辞書が、

```
日本語: エクスポート
```

とすればそちらが勝ちます。

これはユーザー視点では便利ですが、開発者視点では、

**「自分が配布したUIが自分の管理外の辞書によって変更される」**

ということでもあります。

ただし、翻訳システムとしては合理的です。

例えば、

```
作者翻訳     ↓コミュニティ修正     ↓ユーザー独自修正
```

という階層を作れるからです。

# 12\. Cloud/CDN部分は、私は自分のプロジェクトでは切り離す

i18n+はCDNから辞書を取得する仕組みまで持っています。

現在の実装ではデフォルトCDNとして、

```
cdn.jsdelivr.net/gh/open-obsidian-i18n/dictionaries@latest
```

を使用しています。[![](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com&sz=128)GitHub](https://raw.githubusercontent.com/open-obsidian-i18n/i18n-plus/main/src/main.ts)

これは「翻訳をコミュニティで配る」という目的には非常に便利です。

しかし個人プラグインなら、

```
自分のプラグイン      ↓CDN      ↓翻訳JSON
```

というruntime dependencyを増やす必要はありません。

特に、

-   オフライン
    
-   長期利用
    
-   Vaultのバックアップ
    
-   将来のサービス終了
    
-   翻訳内容の再現性
    

を考えると、

**組み込み辞書を基本にした方が堅い**です。

# 13\. 「最後に成功したlocale」fallbackも私は採用しない

これは面白いアイデアですが、個人的には不要です。

例えば、

```
現在 locale = ja
```

なのに、

```
ja dictionaryにkey Aがない
```

とします。

i18n+は、

```
last successful locale
```

を探します。[![](https://www.google.com/s2/favicons?domain=https://raw.githubusercontent.com&sz=128)GitHub](https://raw.githubusercontent.com/open-obsidian-i18n/i18n-plus/main/templates/adapter.ts)

しかしこれは翻訳品質の観点では、

```
UIの一部日本語
UIの一部中国語
UIの一部英語
```

という混在を発生させます。

通常は、

```
ja ↓en ↓key
```

の方が予測しやすいです。

私は、

```
external current locale    ↓builtin current locale    ↓base locale (en)    ↓key
```

で十分だと思います。

# 17\. さらに「i18n+互換」を意識しておくと非常に良い

ここが今回の調査で私が一番推したい部分です。

**i18n+を導入するのではなく、i18n+に接続可能な構造にしておく。**

つまり、

```
┌──────────────┐                │ Built-in i18n│                └──────┬───────┘                       │                       ▼                     t()                       ▲                       │              ┌────────┴────────┐              │                 │       Built-in locale   External dictionary                              │                              ▼                         i18n+ adapter
```

という設計です。

最初は、

```
external dictionary = なし
```

でいい。

将来、

> このプラグイン、翻訳したい

という人が出たら、

```
i18n+
```

に接続できる。

この方式なら、

**今の実装コストは小さいのに、将来の拡張性は残せます。**

* * *

# 18\. そしてi18n+から借りるべきなのは「実装」より「インターフェース」

具体的には、

```typescript
interface I18n {    t(key: string, params?: Record<string, string | number>): string;    getLocale(): string;    setLocale(locale: string): void;}
```

くらい。

そして、

```typescript
const i18n = createI18n({    baseLocale: "en",    locales: {        en,        ja,    },});
```

とする。

これなら、

```
あなたのコード     │     ▼   I18n     │     ├── Built-in     │     └── External
```

になります。

後で、

```typescript
i18n.loadDictionary("zh", dict);
```

を追加するだけでi18n+方式に近づけられます。

# 20\. 「事故実装で十分」か？

ここは少しだけ言葉を変えると、

**「i18nライブラリを導入せず、自分で20～50行程度のi18nを作る」**

という意味なら、私は **それで十分**だと思います。

ただし、

```typescript
if (locale === "ja") ...else ...
```

を各所に書くような「事故実装」は勧めません。

最低限、

```
t()localedictionaryfallback
```

の4つだけは抽象化する。

これだけで十分です。

# 21\. 逆にi18n+を採用する価値が出てくる条件

以下のどれかに該当するなら、i18n+の価値が急激に上がります。

### A. 5～10言語以上を扱う

```
enjazhzh-TWkodefres...
```

となってくると辞書管理が面倒になります。

### B. Community translationを受け入れたい

これがi18n+の本命です。

作者が、

```
enja
```

しか管理しなくても、

```
community ├─ zh ├─ ko ├─ de └─ fr
```

を提供できる。

### C. ユーザーが翻訳を修正できるようにしたい

Overlayはかなり良い機能です。

### D. 複数の自作プラグインを作る

これはかなり重要。

例えばあなたが今後、


# 1\. あなたのプロジェクトで一番重要なのは「翻訳」ではなく「upstream追従」

ここがポイントです。

普通のプラグイン作者なら、

```
自分が開発 ↓自分で翻訳 ↓リリース
```

なので、i18nの設計だけ考えればいい。

しかしあなたの場合は、

```
Original Plugin       │       │ upstream update       ▼   AIによる追従       │       ├── original changes       │       ├── Japanese translation       │       ├── other translations       │       └── your modifications              │              ▼        Forked Plugin
```

です。

つまり重要なのは、

**「翻訳情報をソースコードの変更からどれだけ独立させられるか」**

です。

この観点では、i18n+の設計にはかなり参考になるところがあります。

* * *

# 2\. むしろ「翻訳をコードから分離する」ことが最重要

例えばフォークしたプラグインの元コードが、

```typescript
new Setting(container)    .setName("Enable notifications")    .setDesc("Show notifications when...");
```

だったとします。

あなたがこれを、

```typescript
new Setting(container)    .setName("通知を有効にする")    .setDesc("通知を表示します...");
```

と直接改変すると、upstreamが、

```typescript
new Setting(container)    .setName("Enable notifications")    .setDesc("Show notifications when...")    .addToggle(...)
```

と変更した場合、

**AIがupstream mergeするときに、日本語化部分と機能変更部分が衝突します。**

これは非常に嫌な構造です。

* * *

## ところが、

```typescript
.setName(t("Enable notifications")).setDesc(t("Show notifications when..."))
```

なら、

```
upstream   │   └── 英語コードを更新             │             ▼        自分のコード             │             ▼       t()は変更不要
```

となります。

つまり、

> **i18nは翻訳機能というより、upstream追従時の差分を減らすための「変更分離機構」**

として価値があります。

これはあなたの用途ではかなり重要です。

# 3\. この用途なら「原文key方式」がむしろ非常に相性が良い

前回答では、


のようなsemantic keyの方が一般的には良い、と説明しました。

しかし、あなたの用途では私は評価を変えます。

**原文をkeyにする方式はかなり有力です。**

例えば、


なら、


です。

という処理が非常に簡単になります。

# 結論

今回の前提なら、私は前回答より明確に、

> **自己実装寄りを推します。**

ただし「自分で適当に翻訳機能を書く」という意味ではありません。

**i18n+の方式を参考に、upstream追従に強い最小限のi18n層を自己実装する**という意味です。

特に、

1.  **原文をtranslation keyにする**
    
2.  **英語をsource of truthにする**
    
3.  **翻訳をコードから分離する**
    
4.  **`t()`という薄いAPIだけをコード側に入れる**
    
5.  **翻訳keyの追加・削除・変更を自動検出する**
    
6.  **placeholderの整合性を自動検証する**
    
7.  **AIはupstream mergeと翻訳を別工程として処理する**
    
8.  **将来i18n+など外部辞書へ接続できる余地を残す**
    

という設計が、あなたの目的にはかなり合っています。

そして、**フォーク対象が増えてきた段階で「共通i18n基盤」を切り出す**。この順番がよいと思います。

なお、既存のObsidian翻訳系にも、更新で翻訳が壊れる問題を避けるため「既存辞書を再適用する」仕組みを持つものがあります。これはまさにあなたが考えているupstream追従問題と同じ方向の課題です。[![](https://www.google.com/s2/favicons?domain=https://github.com&sz=128)GitHub](https://github.com/Obsidian-Forge/obsidian-i18n/wiki/%E8%AE%BE%E7%BD%AE%E9%A1%B9%E8%AF%A6%E8%A7%A3)

つまり今回の構想では、**i18nそのものより「upstreamのコード変更に対して翻訳をどう安定して追従させるか」を中心に設計するべき**だと思います。

> [!QUESTION] User
> upstreamから自分のリポジトリにfork、Google Antigravityで多言語化実装、続けて日本語リソース実装、Github Actionのcronでupstreamの更新を１日１回検知。検知したらGoogle Julesで、差分に対して多言語化＋日本語リソースを行う。という自動ループを考えてるのだが、どう思う？

**ChatGPT:**

かなり良い構成だと思います。特に、**「コードのupstream追従」と「翻訳」を人間の手作業から切り離し、GitHub上のPRとして閉じる**のがポイントです。

ただし、私は1点だけ大きく変更します。

> **Julesに「差分に対して多言語化＋日本語リソースを行わせる」のではなく、まず「upstream差分を自分のforkへ取り込む」ことと、「i18n差分を処理する」ことを分離する。**

この方がかなり壊れにくくなります。

## 推奨する全体像

```
upstream repository                         │                    1日1回 cron                         │                         ▼                  更新があるか？                         │                    ┌────┴────┐                    │         │                   No        Yes                    │         │                    │         ▼                    │     update branch                    │         │                    │         ▼                    │      Jules                    │         │                    │   ┌─────┴─────┐                    │   │           │                    │   ▼           ▼                    │ upstream    i18n                    │ changes     changes                    │   │           │                    │   └─────┬─────┘                    │         ▼                    │       tests                    │         │                    │         ▼                    │       PR作成                    │                    └──────────────
```

ただし実際には、もう少し分けた方がいいです。

* * *

# 1\. 最初の一回だけAntigravity

これは非常に合理的です。

### 初期セットアップ

```
upstream   ↓Fork   ↓Antigravity   ↓i18n化   ↓日本語リソース作成   ↓動作確認   ↓GitHub
```

ここではAIにかなり大きな変更をさせていい。

例えば、

```
main.tssettings.tscommands.tsviews/*.ts
```

を調査して、

```typescript
t("Settings")t("Enable notifications")t("Export")
```

に変換。

そして、

```
locales/  en.json  ja.json
```

を作る。

このフェーズは人間がレビューして、

> 「このプラグインのi18n方式はこれで確定」

とします。

* * *

# 2\. その後のJulesは「初回実装を再現」するのではなく「差分を処理」

ここが重要です。

毎回Julesに、

> プラグインを多言語化してください

ではなく、

> upstreamとの差分を確認し、自分のi18n規約に従って必要な変更だけ行え

とする。

例えばupstreamが、

```diff
+ new Setting(container)+   .setName("Enable cache")+   .setDesc("Cache downloaded files")
```

を追加した場合、

Julesは、

```diff
+ new Setting(container)+   .setName(t("Enable cache"))+   .setDesc(t("Cache downloaded files"))
```

にして、

```diff
+ "Enable cache": "キャッシュを有効にする",+ "Cache downloaded files": "ダウンロードしたファイルをキャッシュします"
```

を追加する。

これなら非常に機械的です。

* * *

# 3\. 「多言語化」と「日本語化」は実際には別タスク

ここは分離した方がいいです。

例えば、

```
Source  ↓i18n化  ↓en.json  ↓ja.json
```

です。

つまり、

### Task A

**コードから翻訳可能な文字列を抽出する**

### Task B

**日本語訳を作る**

です。

この2つをJulesに一度にやらせてもいいのですが、内部的には別ステップとして考える。

* * *

# 4\. さらに「多言語化」と「多言語翻訳」を分ける

これはもっと重要です。

あなたが必要なのは、

> 多言語化されたプラグイン

であって、

> 全言語に翻訳されたプラグイン

ではない可能性が高い。

つまり、

```
i18n対応    ↓English source    ↓Japanese
```

までを必須にする。

その他の、

```
zhkodefres
```

は後から追加できる。

この構造にしておけば、将来コミュニティ翻訳やi18n+のような仕組みに接続できます。

* * *

# 5\. GitHub Actionsはかなり相性がいい

cronで、

```yaml
on:  schedule:    - cron: "0 3 * * *"
```

のように1日1回チェック。

ただし、

**cronのAction自身にJulesを全部やらせない**

方がいいと思います。

例えば、

```
GitHub Action    │    ├─ upstream fetch    ├─ compare HEAD    └─ 更新あり？             │             ▼       Jules起動
```

という役割分担。

GitHub Actionは**オーケストレーター**にします。

* * *

# 6\. 更新検知と更新処理を分ける

私はリポジトリに、

```
.github/  workflows/    upstream-check.yml    upstream-update.yml
```

の2段階を置きたいです。

### upstream-check

```
毎日 ↓upstream fetch ↓差分確認 ↓差分なし → 終了差分あり → Issue/PR/dispatch
```

### upstream-update

```
Jules ↓upstream merge ↓i18n適用 ↓翻訳更新 ↓test ↓PR
```

こうすると障害時の切り分けが非常に楽です。

* * *

# 7\. 「JulesがPRを直接更新」より「専用branchを作る」

例えば、

```
upstream-sync/2026-08-15
```

というbranch。

```
main  │  └── upstream-sync/2026-08-15          │          ├── upstream merge          ├── i18n          ├── ja          └── tests
```

そして、

```
GitHub PR
```

を作る。

これならあなたは、

> 差分を確認 → Merge

だけで済みます。

* * *

# 8\. ここで「AIに何を任せるか」が重要

私は以下のようにします。

| 処理 | AI | deterministic script |
| --- | --- | --- |
| upstream更新検知 |  | ○ |
| upstream merge | △ | ○ |
| UI文字列抽出 | ○ | ○ |
| i18nコード変換 | ○ | ○ |
| 日本語翻訳 | ○ |  |
| key整合性確認 |  | ○ |
| placeholder確認 |  | ○ |
| build |  | ○ |
| test |  | ○ |
| PR作成 |  | ○ |

つまり、

> **AIに判断させるところと、機械的に検証できるところを分ける。**

これが重要です。

* * *

# 9\. 特に「upstream merge」はJulesに全部任せなくていい

ここは私なら、

```
git fetch upstreamgit merge upstream/main
```

自体はGitHub Actionでやらせます。

そしてmerge conflictが起きた場合だけ、

```
Jules
```

に渡します。

つまり、

```
No conflict    ↓自動
Conflict    ↓Jules
```

です。

これはかなり安全です。

* * *

# 10\. そして「i18n化済み」という状態を機械的に保証する

ここで前に話した自己実装i18nが効いてきます。

例えば、

```
scripts/check-i18n
```

を作る。

チェック内容は、

### ① source key

```
t("Enable notifications")
```

### ② en

```json
"Enable notifications": "Enable notifications"
```

### ③ ja

```json
"Enable notifications": "通知を有効にする"
```

が全部存在するか。

さらに、

### ④ 未翻訳

```json
"Enable cache": "Enable cache"
```

を検出。

### ⑤ obsolete

```json
"Old setting": "古い設定"
```

を検出。

### ⑥ placeholder

```
{count}{name}{path}
```

の一致を確認。

これをGitHub Actionで実行する。

* * *

# 11\. これをやるとJulesの性能に依存しすぎなくなる

ここが非常に重要です。

悪い構造は、

```
Jules ↓ちゃんと多言語化できたはず ↓たぶんOK
```

です。

良い構造は、

```
Jules ↓変更 ↓check-i18n ↓build ↓test ↓OK / NG
```

です。

Julesが間違えても、

**CIが止める。**

この構造ならAIをかなり大胆に使えます。

* * *

# 12\. i18n+をここでどう位置付けるか

今回の構想なら、私はこうします。

```
あなたのi18n                         │              ┌──────────┴──────────┐              │                     │           built-in             external              │                     │        en.json / ja.json      optional                                    │                                    ▼                                  i18n+
```

つまり、

**i18n+を必須依存にはしない。**

しかし将来的に、

> 「この翻訳を他の人にも配布したい」

となったら外部辞書としてi18n+を利用できるようにする。

これが非常にきれいです。

* * *

# 13\. そして、あなたの方式なら「原文key」がかなり強い

例えば、

```typescript
t("Enable notifications")
```

を使っておけば、Julesに、

> upstream diffから追加されたUI文字列を探して、`t()`でラップし、en/ja resourceを更新せよ。

というかなり具体的な指示ができます。

semantic key方式だと、

```
settings.notifications.enable
```

をJulesが新しく考えないといけない。

その判断自体がAIタスクになります。

一方原文keyなら、

```
upstream string       ↓translation key
```

が一意です。

**upstream追従AIとの相性はこちらの方がいいです。**

* * *

# 14\. 一つだけ注意したいのが「英語文字列の変更」

例えばupstreamが、

```
"Enable cache"
```

を

```
"Enable caching"
```

に変更した場合。

原文key方式なら、

```
削除:"Enable cache"
追加:"Enable caching"
```

と認識できます。

Julesは、

```
ja:"キャッシュを有効にする"
```

を新しいkeyに移す。

これは自動化できます。

ただし、

> **単なる文言修正なのか、意味が変わったのか**

はAI判断になります。

ここだけは完全なdeterministic処理にしなくていいです。

* * *

# 15\. 私なら「翻訳メモリ」も持たせる

あなたの構想なら、さらに一段進める価値があります。

例えば、

```
translation-memory.json
```

に、

```json
{  "Enable cache": {    "ja": "キャッシュを有効にする"  }}
```

を保存する。

upstreamが、

```
Enable cache
```

を再利用したら、

**既存訳をそのまま使う。**

AIに毎回翻訳させない。

これにより、

-   翻訳品質の安定
    
-   AIコスト削減
    
-   表現の統一
    
-   upstream更新時の処理高速化
    

が得られます。

# 18\. AntigravityとJulesの役割分担も良い

今回の使い分けは合理的です。

### Google Antigravity

**初期開発・大規模変更**

-   リポジトリ全体を理解
    
-   i18nアーキテクチャ導入
    
-   既存コードを一括変換
    
-   日本語リソース作成
    
-   テスト追加
    

### Google Jules

**反復的な保守**

-   upstream差分確認
    
-   小規模コード変更
    
-   翻訳追加
    
-   resource更新
    
-   PR作成
    

という分担。

これはかなり自然です。

* * *

# 19\. 一番重要なのは「Julesに自由度を与えすぎないこと」

Julesへの指示は、

> 「upstreamを追従して日本語化して」

ではなく、

```
1. upstreamとの差分を確認2. upstreamの変更以外を変更しない3. i18n規約に従う4. 新規UI文字列をt()へ変換5. en resourceを更新6. ja resourceを更新7. 既存の日本語訳を勝手に変更しない8. I18N.mdの用語を遵守9. check-i18nを実行10. build/testを実行11. 失敗したらPRを作らず原因を報告
```

くらいまで**プロトコル化**した方がいいです。

* * *

# 20\. 総合評価

この構想自体は、私は **かなり良いと思います。8.5～9/10くらい**です。

特に良いのは、

-   Forkという明確なupstream境界
    
-   初回だけ大規模AI作業
    
-   以降は差分追従
    
-   GitHub Actionsによる定期検知
    
-   Julesによる反復作業
    
-   PRで人間が最終確認
    

という構造です。

改善ポイントは、

> **「Julesに全部やらせる」のではなく、「GitHub Actions + deterministic scripts + Jules」で三層化する**

こと。

そしてi18nについては、

> **i18n+を今すぐ依存する必要はない。まず自己実装し、i18n+の外部辞書思想と互換性を意識する。**

というのが、この運用モデルでは一番合理的だと思います。

むしろこのプロジェクトの場合、**i18nのライブラリ選定より、`upstream → AI → i18n → 翻訳 → CI → PR`という自動化パイプラインの設計の方が圧倒的に重要**です。

もしこの方式を実際に作るなら、次に詰めるべきなのは \*\*「フォークした任意のObsidianプラグインを、このパイプラインに載せるためのリポジトリ構造・GitHub Actions・Julesへの指示書・i18n仕様をどう標準化するか」\*\*です。ここを一度設計してしまえば、2個目、3個目のフォークからはかなり機械的に増やせます。
